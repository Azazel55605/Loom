# Component registry

The living inventory of every UI component in Loom. Conventions governing how
these are built live in [`UI_GUIDELINES.md`](./UI_GUIDELINES.md) and change
rarely; this file changes constantly.

The shared UI kit in `crates/core` has not been started yet, so each client
carries its own copy under `apps/<app>/src/components/`. Several components are
now duplicated across `web-frontend`, `desktop` and `mobile` — that duplication is
precisely what the shared kit is meant to remove, and the "Used in" column below
is what makes it visible. Components consumed by more than one client should
move into the kit once it exists.

| Component | Source | Variants | Used in | Notes |
| --------- | ------ | -------- | ------- | ----- |
| `Card` | shadcn | — | web-frontend, desktop, mobile | Includes `CardHeader`, `CardTitle`, `CardDescription`, `CardContent`, `CardFooter`. Uses the `.surface-elevated` class so the blur/reduced-transparency tokens apply. |
| `Badge` | shadcn-extended | `default`, `secondary`, `destructive`, `outline`, `healthy`, `degraded`, `down`, `unknown` | web-frontend, desktop, mobile | `default` resolves from the accent token via Tailwind's `primary` colour. The four health variants were added in web-frontend for connector status and resolve from the `--status-*` tokens in `index.css` — semantic status colours with fixed hues, deliberately **not** accent-derived, so "healthy" keeps meaning healthy when the user picks a red accent. Desktop and mobile still carry the unextended copy; they gain the variants when they gain a connector view. |
| `Skeleton` | shadcn | — | web-frontend | Loading state for the connector list (placeholder cards matching the real layout, so it does not jump when data lands). Animation is suppressed by the global `prefers-reduced-motion` rule in `index.css`. |
| `Alert` | shadcn | `default`, `destructive` | web-frontend, desktop, mobile | Includes `AlertTitle`, `AlertDescription`. Error state for an unreachable backend; icon from `lucide-react`. |
| `Input` | shadcn | — | web-frontend, desktop, mobile | Used as-is for the server URL field (desktop, mobile) and the login form (web-frontend). Themed replacement for a native `<input>`, per docs/UI_GUIDELINES.md. The web-frontend copy is byte-identical to the desktop one. |
| `Button` | shadcn | `default`, `destructive`, `outline`, `secondary`, `ghost`, `link` (sizes `default`, `sm`, `lg`, `icon`) | web-frontend, desktop, mobile | Submit control for the server URL form (desktop, mobile); login submit, sign-out, and connector action buttons (web-frontend). The web-frontend copy is byte-identical to the desktop one. |
| `ServerUrlField` | custom | — | desktop, mobile | Thin composition of `Input` + `Button`, not a new primitive — it adds the form wrapper (submit on Enter) and labelling only. Exists because desktop builds must reach a user-chosen server at runtime, whereas web-frontend bakes its API URL in at build time. No Radix primitive needed: the underlying elements are already shadcn components. |
| `Label` | shadcn | — | web-frontend | Wraps `@radix-ui/react-label`, which handles the click-to-focus association a bare `<label>` only gets right by convention. Used through `FormLabel` rather than directly. |
| `Form` | shadcn | — | web-frontend | react-hook-form bindings: `Form`, `FormField`, `FormItem`, `FormLabel`, `FormControl`, `FormDescription`, `FormMessage`, `useFormField`. Taken as-is for the accessibility wiring — it associates an error message with the input that produced it via `aria-describedby`/`aria-invalid`, which is exactly what rots when written per form by hand. Validation is zod through `@hookform/resolvers`. |
| `Toaster` | shadcn | — | web-frontend | Sonner, mounted once in `main.tsx`. Reads `useAppearance()` for the resolved light/dark palette and passes it to Sonner's `theme` prop — the same thing shadcn's own wrapper does with `next-themes`. Our classes set the toast background, but Sonner ships defaults keyed off that prop at the same specificity, so leaving it on `light` risks a white toast with light text the moment the two rules are ordered differently. Sonner is shadcn/ui's current toast component upstream, having replaced the older `Toast`/`useToast` pair. Restyled from the shared tokens (`.surface-elevated`, `--border`, accent) rather than Sonner's own palette, so the blur and reduced-transparency settings reach it. Respects `prefers-reduced-motion`. |
| `AppShell` | custom | — | web-frontend | The signed-in chrome: sticky header with the product name (linking home), the backend's core version, a settings entry point, the current user, and sign-out. The settings link is visible to any authenticated user — the tabs inside handle further gating — and is styled with `buttonVariants` on a router `Link` rather than by giving `Button` an `asChild` prop, so `Button` stays as it is. Built from `Button` + `Badge` plus layout; no Radix primitive because it owns no interactive behaviour of its own. Uses `.surface-elevated` so the blur tokens apply to the header. |
| `ConnectorCard` | custom | — | web-frontend | One connector: name, id, icon identifier, version, a health `Badge`, the last-checked time, and one `Button` per `ConnectorAction` returned by the API. Composition of `Card` + `Badge` + `Button` + `Alert`; no Radix primitive needed. Distinguishes a connector reporting `down` (a successful status check) from one Loom could not read at all (`status: null` + `statusError`), which are different states and render differently. Action buttons show a per-button spinner while pending and report the outcome through `Toaster`. |
| `SetupForm` | custom | — | web-frontend | The first-run wizard in `src/pages/SetupPage.tsx`: instance name, admin username, password, confirm password. Built from `Form` + `Input` + `Button` + `Alert` inside a `Card`, same pattern as `LoginForm`; no new primitive. Password confirmation is a zod `.refine` attached to the confirm field's path, so the message appears where the fix is. Not a separately exported component — it is the page's only content and has no second consumer. |
| `LoginForm` | custom | — | web-frontend | The login card in `src/pages/LoginPage.tsx`, built from `Form` + `Input` + `Button` + `Alert` inside a `Card`. Not a separate exported component — it is the page's only content and has no second consumer, so extracting it would add indirection without removing duplication. Listed here because it is where the `Form` pattern is exercised. Delegates entirely to the auth context, so moving to access + refresh tokens changed no markup here. |
| `Tabs` | shadcn-extended | — | web-frontend | Wraps `@radix-ui/react-tabs`. `TabsList` uses `.surface-panel` instead of `bg-muted`, so it is identical at the `off` and `standard` blur levels and frosted at `extra` without a second class. Includes `TabsList`, `TabsTrigger`, `TabsContent`. The settings section nav. Driven by the URL rather than internal state, so a settings page is linkable — `SettingsLayout` reads the location and the triggers navigate. `TabsContent` is unused there because the panels are router `Outlet` children. Stock shadcn's `hover:bg-accent` was changed to the neutral `muted` token: in this codebase `accent` is the user's accent colour, not shadcn's neutral hover. |
| `Table` | shadcn | — | web-frontend | `Table`, `TableHeader`, `TableBody`, `TableRow`, `TableHead`, `TableCell`, `TableCaption`. Plain semantic `<table>` elements with token styling and no Radix primitive — a table is already the accessible construct for tabular data, and the no-native-controls rule is about *form controls* the browser renders in its own chrome. `Table` wraps itself in an `overflow-auto` container so a wide table scrolls inside its own box rather than widening the page. Used by `UsersPanel` and `GroupsPanel`. |
| `Dialog` | shadcn | — | web-frontend | Wraps `@radix-ui/react-dialog`; the themed replacement for a native `<dialog>`. Radix owns focus trapping, scroll locking, `aria-modal`, and Escape dismissal. Content uses `.surface-elevated` so the blur and reduced-transparency tokens reach it, with contrast from the solid fallback rather than the blur. Holds the create/edit forms in `UsersPanel` and `GroupsPanel`. |
| `AlertDialog` | shadcn | — | web-frontend | Wraps `@radix-ui/react-alert-dialog`. **Deliberately distinct from `Dialog`, not a variant of it:** Radix gives it `role="alertdialog"`, focuses cancel first, and refuses outside-click and Escape dismissal — so "click anywhere else" is not a valid answer to "delete this user?". Reserved for destructive confirmation; anything containing a form is a `Dialog`. `AlertDialogAction`/`AlertDialogCancel` render through `buttonVariants`. Both panels call `preventDefault` on the action so the dialog survives a 409 refusal and the explanation lands somewhere that still exists. |
| `Switch` | shadcn | — | web-frontend | Wraps `@radix-ui/react-switch`. The active/inactive toggle in the edit-user dialog. Checked state resolves from `--accent` via Tailwind's `primary`. Motion is a `translate-x` transition that the global `prefers-reduced-motion` rule reduces to an instant swap — state stays visible either way, since thumb position *and* track colour both convey it. |
| `Checkbox` | shadcn | — | web-frontend | Wraps `@radix-ui/react-checkbox`; the themed replacement for a browser-default checkbox. Radix renders a hidden native input for form participation while the visible box is ours. Used by `GroupMultiSelect` and `PermissionGrantBuilder`. |
| `Select` | shadcn | — | web-frontend | Wraps `@radix-ui/react-select`. The connector scope picker in `PermissionGrantBuilder`. This is the control the no-native-controls rule exists for — a native `<select>` renders as a Windows combobox, a macOS popup, a GTK menu, and a full-screen iOS wheel. Content uses `.surface-elevated`; item focus uses the `muted` token rather than stock shadcn's `accent`, as with `Tabs`. |
| `SettingsLayout` | custom | — | web-frontend | The settings chrome: `AppShell` plus a `Tabs` bar over the `/settings/*` sub-routes, with the panels rendered as router `Outlet` children. Composition, not a new primitive — `Tabs` owns the interactive behaviour. Tabs are rendered per permission (`users.manage`, `groups.manage`) via `hasPermission`, which is **visibility only**: deep-linking to a hidden section still renders its panel, and the panel's queries come back 403. The backend is the enforcement point. |
| `UsersPanel` | custom | — | web-frontend | `/settings/users`: a `Table` of accounts with status and membership `Badge`s, a create `Dialog`, an edit `Dialog` (`Switch` + `GroupMultiSelect`), and a delete `AlertDialog`. Composition of existing primitives. Handles the backend's 409 safeguards as their own case — the message is shown verbatim because it is written to be read ("that would leave no active administrator" is instruction; "something went wrong" is not). Degrades to raw group ids when `GET /groups` 403s, which is what a `users.manage`-only account sees. |
| `GroupsPanel` | custom | — | web-frontend | `/settings/groups`: a `Table` of groups with a Protected `Badge`, one `Dialog` shared by create and edit, and a delete `AlertDialog`. The delete control is **not rendered at all** for a protected group rather than rendered-and-refused — a control existing only to produce a 409 teaches people that errors are normal. One dialog serves both operations because `PATCH` states the whole grant set exactly as `POST` does. |
| `PermissionGrantBuilder` | custom | — | web-frontend | The grant editor shared by the create and edit group dialogs — its own component precisely because it has two consumers. Rows come from `GET /permissions`, never a hardcoded list: the `permissions` table is authoritative, so a hardcoded form would be quietly wrong rather than visibly broken after the next migration. Every grant is global except `connectors.control`, which may be narrowed to one connector via `Select`. That scoping is deliberately specific rather than a generic resource-type picker — `connector` is the only resource type that exists today. Composition of `Checkbox` + `Select` + `Label`. |
| `GroupMultiSelect` | custom | — | web-frontend | Group membership as a `Checkbox` list rather than a multi-select popover: membership is small and enumerable, and better read all at once than summarised as "3 selected". Controlled, and it states the whole selection on every change, mirroring the API's replace-wholesale `groupIds`. Shown as a disabled explanation when the group list could not be read. |
| `Avatar` | shadcn | — | web-frontend | Wraps `@radix-ui/react-avatar`; includes `AvatarImage` and `AvatarFallback`. The fallback is the reason to use the primitive rather than a bare `<img>`: Radix tracks the image's load state and swaps in initials when the source is missing, still loading, or broken — which is exactly the set of states an `avatarUrl` has. A hand-rolled version reaches for `onError` and still flashes a broken-image icon first. |
| `SettingsLayout` | custom | — | web-frontend | Restructured: the top-level tabs are now General, Account, Appearance, Permissions. The first three are visible to every authenticated user — Account only ever touches the caller's own row, and Appearance never leaves the browser — while Permissions needs `users.manage` **or** `groups.manage`. Active-tab detection reads only the third path segment, so a nested route like `/settings/permissions/groups` still lights up the Permissions tab. |
| `PermissionsLayout` | custom | — | web-frontend | The Permissions section: a smaller nested `Tabs` bar over `UsersPanel` and `GroupsPanel`, which moved under `/settings/permissions/*` unchanged. **The sub-nav renders only when the user holds both grants** — a tab list with one tab is not navigation, it is a label pretending to be a control, and it invites "what is the other one?" for a section the user cannot reach. Exports `PermissionsIndexRedirect` alongside it, because which subsection `/settings/permissions` lands on depends on the caller's grants and so has to be a component rather than a fixed route target. |
| `AccountPanel` | custom | — | web-frontend | `/settings/account`: avatar, profile form, and `PasswordChangeForm`. A 409 on the username is surfaced as a **field-level** error rather than a toast — that input is what has to change, and a toast leaves the user staring at a form with no indication of which field is at fault. The avatar section pairs a `sr-only` file input with a `buttonVariants`-styled `<label>`: `sr-only` rather than `display:none` because a hidden input is not focusable, which would put the control out of reach of a keyboard user. Upload errors show the backend's own message (too large, not a decodable image), since the backend decides by decoding the bytes and its wording is the only useful part. |
| `PasswordChangeForm` | custom | — | web-frontend | Its own component and its own form, deliberately separate from the profile form: it is a separate transaction needing the current password as proof, and combining them would make someone changing their display name think about their password. A 401 means the *current password* was wrong — not an expired session — so it sets a field-level error and **leaves the new-password fields intact**; only success clears the form. The API client opts this call out of its automatic refresh-and-retry so that distinction survives the transport. |
| `AppearancePanel` | custom | — | web-frontend | `/settings/appearance`: theme, accent swatches, a custom hex field, a three-level blur `SegmentedControl`, and a motion `Switch`. No save button — every change applies and persists immediately, which is the honest interaction for settings whose whole effect is already visible. The motion switch shows as checked-and-disabled when the OS asks for reduced motion, because it genuinely is on and the app must not be able to lower that floor. Carries an on-screen note that these are per-device. |
| `ColorSwatchPicker` | custom | — | web-frontend | Accent presets as eight swatches at consistent saturation and lightness, so none reads as conspicuously darker than its neighbours in either theme. Also exports `hslToHex`/`hexToHsl`: the stored form is always bare HSL channels, and hex exists only at the edge where people type colours. Selection is shown by a ring **and** a check mark — a ring around a coloured circle is easy to miss and invisible to someone who cannot distinguish the hues. Still built as `aria-pressed` buttons. `RadioGroup` now exists (added for `SegmentedControl`), so the note that once deferred this no longer applies — converting the swatches to it would gain arrow-key navigation and a single tab stop, and is a small, worthwhile follow-up rather than something this change needed. |
| `RadioGroup` | shadcn | — | web-frontend | Wraps `@radix-ui/react-radio-group`; includes `RadioGroupItem`. The accessible construct for "exactly one of these". Radix supplies the part that is tedious and easy to get wrong: roving focus, so the group is a single tab stop and the arrow keys move between options. |
| `SegmentedControl` | custom | — | web-frontend | `RadioGroup` re-skinned as side-by-side labelled segments — the same primitive, a different surface, which is step (b) of the sourcing rule. Used for Theme and Blurred surfaces. Preferred over `Select` for three-or-fewer short options, where every choice being visible without opening anything is the point. The selected segment reads as a raised surface, matching `TabsTrigger`, so the two controls look related. |
| `AccentThemeProvider` | custom | — | web-frontend, desktop, mobile | Theme provider, not a visual component. Stateful and `localStorage`-backed: it owns the accent (`--accent`), the blur **level** (`off` / `standard` / `extra`, one root class each), motion (`.reduce-motion`), and the light/dark palette (`.dark` plus `color-scheme`). All are read during `useState` initialisation so no frame paints with the wrong values first. Exposes `useAppearance()` (renamed from `useAccentTheme`, since it is no longer only about accent). The blur setting used to be a boolean; the old `loom-blur-enabled` key is still read once so an existing choice is not silently reset. `prefers-reduced-motion` is a floor the in-app switch may raise but never lower; `prefers-reduced-transparency` and `prefers-color-scheme` are only defaults, which an explicit choice overrides in either direction. Desktop and mobile still carry the older accent-only copy. |
