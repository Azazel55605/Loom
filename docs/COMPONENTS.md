# Component registry

The living inventory of every UI component in Loom. Conventions governing how
these are built live in [`UI_GUIDELINES.md`](./UI_GUIDELINES.md) and change
rarely; this file changes constantly.

The shared React UI and client logic live in `packages/ui-kit`. Web/frontend,
Desktop, and Mobile consume that package. Each installed app keeps only thin
router, persistence, and native-transport adapters.

| `Toaster` | `packages/ui-kit/src` | shadcn | — | web-frontend, desktop, mobile | Sonner, mounted once in `main.tsx`. Sonner is shadcn/ui's current toast component upstream, having replaced the older `Toast`/`useToast` pair. Restyled from the shared tokens (`.surface-elevated`, `--border`, accent) rather than Sonner's own palette, so the blur and reduced-transparency settings reach it. Respects `prefers-reduced-motion`. |
| `AppShell` | `packages/ui-kit/src` | custom | expanded/collapsed sidebar | web-frontend, desktop, mobile | The signed-in chrome: full-width sticky header, backend core version, current user, and sign-out. All three clients supply `DashboardSidebar`. The sidebar is anchored to the viewport's left edge and can be hidden with the header trigger or Ctrl/Cmd+B; that per-device choice is persisted best-effort in `localStorage`. Uses `.surface-elevated`/`.surface-panel` so the blur tokens reach both header and sidebar. |
| `DashboardSidebar` | `packages/ui-kit/src` | custom | shell expanded/collapsed; section expanded/collapsed | web-frontend, desktop, mobile | Collapsible Pinned, My Dashboards, and Shared with me sections backed by `GET /dashboards`. The whole panel is collapsed by `AppShell`, independently of its section toggles. Pinned entries deliberately also remain in their ownership section. Pin changes are optimistic React Query mutations and role badges distinguish Editor/Viewer shares. Navigation and the optional connector-management footer are injected, keeping React Router out of the shared package. Owns the small new-dashboard dialog and navigates through its callback after creation. |
| `DashboardCreateDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Reusable dashboard-name `Dialog` used by the sidebar and the `/dashboards` first-dashboard empty state. Creates through the shared API client, refreshes the dashboard query, and returns the created summary to platform navigation. |
| `DashboardsIndexView` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Shared `/dashboards` loading, failure, first-dashboard, and preferred-dashboard selection states. Navigation is returned through a callback so browser history versus Tauri hash routing remains app-owned. |
| `DashboardView` | `packages/ui-kit/src` | custom | read-only grid / edit-layout mode | web-frontend, desktop, mobile | Dashboard detail: header with owner-only inline rename, share, and confirmed delete, plus the placement grid itself. Placements are a `react-grid-layout` grid of `DashboardPlacementCard`s, **static until an Owner or Editor turns on Edit layout** — a Viewer never sees that button. That is not only a permission matter: a dashboard is looked at far more often than it is rearranged, and an always-draggable grid turns every attempt to press a button into a chance to move a card. Edit mode also disables the action widgets, so a grab that lands on a toggle cannot restart a service. Six columns and 110px rows are chosen against what `metadata.minSize` claims to mean — a twelve-column grid would make the usual `[2, 2]` one sixth of the page and turn every connector's stated minimum into a lie. Each item carries that `minSize` as its `minW`/`minH`. Holds **one** status-socket subscription for every instance on the dashboard and passes readings down as props; the socket reference-counts, so two placements of one connector cost one subscription. Geometry is persisted on drag-stop and resize-stop only, never per frame, and the **whole** layout is diffed against what is stored rather than just the dragged card — the compactor can move cards the user did not touch. Local layout state updates immediately so nothing snaps back mid-request; a failed PATCH toasts and refetches so the grid shows what the server actually holds. Owns `AddPlacementDialog`, `PlacementBindingsDialog`, and the remove-placement `AlertDialog`. |
| `DashboardSharesDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Owner-only share list and add/remove flow. Uses `SegmentedControl` for User/Group, existing `getUsers`/`getGroups` data in shadcn `Select`s, View/Edit roles, and `AlertDialog` before revocation. Backend errors remain visible at form level, including the 409 message for a duplicate target. |
| `ConnectorsView` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Standalone connector administration at `/connectors` — where instances are created, reconfigured, and deleted. No longer a stand-in for the dashboard now that `DashboardView` renders real widgets; the two answer different questions, and this one stays flat and complete rather than arranged. Loads `GET /connector-instances` once through React Query, subscribes the rendered instance ids through the shared reconnecting status WebSocket, and applies pushed snapshots to the list/detail caches; there is no status refetch timer. Owns the add/edit dialog and delete `AlertDialog`. Empty state is a real invitation with an "Add connector" button — connectors are no longer shipped by default, so zero of them is the normal first state and a blank screen would read as breakage. Loading is `Skeleton` cards matching the real layout. The platform supplies `renderShell`, keeping navigation outside the package. `Add`/`Edit`/`Delete` render only with `connectors.manage`; that is visibility, not enforcement. Desktop and mobile consume it unchanged. |
| `ConnectorCard` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | One connector instance: name, type, icon identifier, version, a health `Badge`, its `displayFields` as label/value rows, and the last-checked time. Fetches its own detail — `GET /connector-instances/{id}`, keyed by instance id — because the list response does not carry `actions`; status fields are then kept current by `ConnectorsView`'s WebSocket cache updates. Everything from the list summary renders immediately and only the action row is a `Skeleton` while that request is in flight. Renders one plain `Button` per action, opening the shared `ActionParamsDialog` for actions whose `paramsSchema` declares properties — that dialog was extracted from this file so the `Button` widget could reuse it rather than grow a second parameter prompt. Actions refetch detail metadata but no longer trigger an ad-hoc list/status request. **Not the widget system** — this is connector *administration*, a flat list of every instance; `dataPoints` and `defaultLayout` are rendered by `DashboardPlacementCard` on a dashboard, not here. Action buttons and the params dialog are gated on `connectors.control`, edit/delete icon buttons on `connectors.manage`; both are visibility only, and the backend re-checks resource-scoped on every request. Composition of `Card` + `Badge` + `Button` + `Alert` + `Dialog` + `Skeleton`. Distinguishes a connector reporting `down` (a successful check) from one Loom could not read at all (`status: null` + `statusError`) — which is also what an instance that failed to load at startup looks like. |
| `SchemaForm` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | A form generated from a JSON Schema document, so registering a connector type on the backend needs no frontend change: the add-connector dialog renders whatever `configSchema` it is handed, and action parameters go through the same component. Composition of `Input` + `Switch` + `Label`; recursive over nested `object` properties. Also exports `defaultsForSchema` and `validateSchemaValues`. **Minimal JSON Schema support: string, number/integer, boolean, and nested objects only.** `enum`, `array`, `oneOf`/`anyOf`/`allOf`, `$ref` and unrecognised types are rendered as a visible "not supported yet" note rather than silently dropped — a field quietly missing from a form is a setting a user can neither set nor see that they cannot set. Validation covers `required` and basic types only and is **not** a JSON Schema validator: the connector's own factory on the backend is authoritative, and its 400 is surfaced by the caller. |
| `ConnectorInstanceDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | One dialog for both adding and reconfiguring an instance, as with `GroupDialog` — the fields and validation are identical and only the request differs. Type list comes from `GET /connector-types` through a `Select` and the configuration form from `SchemaForm`; **nothing here knows what `"debug"` is**, which is the point of the registry. The type is fixed when editing (a different type is a different connector) and auto-selected when only one is registered. Collects `name` separately from connector config. A rejected configuration is shown as a form-level `Alert` carrying the connector's own message, not a toast — the backend names the field to fix, and a generic toast throws that away. The form is `noValidate`: schema `min`/`max` reach the input for the stepper, but the browser's native validation bubble is a browser-default control per UI_GUIDELINES and would pre-empt the connector's better-worded objection. |
| `DashboardPlacementCard` | `packages/ui-kit/src` | custom | read-only / editing | web-frontend, desktop, mobile | One placed connector: card shell (name, type, health `Badge`) plus every widget bound to it, dispatched through `renderWidget`. Draws on **three** sources kept deliberately apart — the placement supplies bindings and geometry, an instance-detail query supplies `dataPoints`/`actions` (labels, units, parameter schemas) under the same `["connector-instance", id]` key `ConnectorCard` uses so two placements of one connector share a request, and the live status arrives as a prop from `DashboardView`'s single socket subscription. Only values change per poll, which is why only they are on the push channel. Detail-loading skeletons the widget area, never the whole card — name and health are already known and reloading them would look like a bug. Charts and log panes are given `col-span-full`; the scalar widgets tile. Owns the action mutation and its toasts, distinguishing a reached-and-declined action (`success: false`) from a failed request, and **rethrows** so the optimistic widgets can roll back. Only the header carries the drag-handle class, so a press on a slider never becomes a drag. The expand-to-modal control is a deliberate disabled stub. |
| `renderWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | Not a component but the dispatcher every widget reaches the page through, and the single place the binding model meets the primitives. Narrows on the binding's tag first — `display` resolves against `dataPoints` and reads `statusDetails[dataPointId]`, `action` resolves against `actions` and receives `onExecute` — which is the split ADR 0014's tagged `WidgetBinding` exists to make checkable. A binding naming something the connector no longer declares renders a labelled note, not nothing: data points change with configuration, and a silently missing widget is indistinguishable from a layout bug. Merges the action's sole parameter name into the widget config so a binding need not restate it. Takes one options object rather than five positional arguments. |
| `getCompatibleWidgetTypes` / `getCompatibleActionWidgetTypes` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | The two lookup tables `PlacementBindingEditor` offers from, in `widgets/compatibility.ts` alongside the display/action widget labels and the `DisplayWidgetKey` ↔ `DisplayWidgetType` conversions (the chart variant is an object, not a string). Number → stat tile, progress bar, gauge; String → stat tile, log stream; Bool → status dot, stat tile; TimeSeries → chart. For actions it is a **heuristic over the same minimal schema slice `SchemaForm` supports** — one top-level `string`/`number`/`boolean` property — and everything it cannot read falls back to `button`, the one control that handles any action by opening the generated form. `button` is therefore always present and always last. Guidance, not enforcement: the backend validates that ids *exist*, never that a widget suits its data. |
| `StatTileWidget` | `packages/ui-kit/src/widgets` | custom | sizes `sm`, `md`, `lg` | web-frontend, desktop, mobile | One reading shown large with its label, and the fallback for anything scalar — offered for three of the four value types. `tabular-nums` is load-bearing, not decorative: a value re-rendering on every status frame jitters horizontally without it, and a number that visibly twitches reads as broken. Booleans render as Yes/No rather than `true`/`false`. |
| `ProgressBarWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A bounded number as a filled `Progress` bar over `config.min`–`config.max` (0–100 default). The bar is a percentage but the **number beside it is the raw reading with its unit** — a bar that silently turned 6 GiB of 16 GiB into "37%" and showed only that would lose what the connector actually reported. `aria-valuetext` carries the raw reading for the same reason. A value outside the bounds clamps the bar but not the label, so a misconfigured `max` looks wrong rather than looking fine. |
| `MetricChartWidget` | `packages/ui-kit/src/widgets` | custom | `line`, `bar`, `pie` | web-frontend, desktop, mobile | Recharts, wrapping a `React.lazy` `MetricChartCanvas` — the library is ~500 kB reaching the app through this one widget, so it is a separate chunk fetched only when a chart is actually drawn, and dashboards without one never pay for it. `chartType` is a **prop, not a config key**: in the corrected binding model it is part of the widget type, so reading it back out of the free-form config would give a hand-edited binding two disagreeing answers. **Line is the variant with a real job** — it plots the `{timestamp, value}[]` shape from `ConnectorStatus.details`. **Pie and Bar want multi-series data no connector produces yet**, so they render the honest minimum (the reading against `config.max`) and become genuinely useful only when a data point can carry categories, which is a connector-contract change. All colours come from CSS variables, never Recharts' defaults; animation is off throughout, since a series that re-animates every poll is unreadable. |
| `GaugeWidget` | `packages/ui-kit/src/widgets` | custom | sizes `sm`, `md`, `lg` | web-frontend, desktop, mobile | A bounded number as a 270° radial dial. shadcn has no gauge, so this is a step-(c) build: no Radix primitive because there is nothing interactive to make accessible — it is one `role="img"` SVG with a text alternative — CVA carries the size variants, and both arcs paint from the token palette. Track and value are two `stroke-dasharray` lengths on **one** arc geometry, so the value can never drift out of alignment with its track. |
| `StatusDotWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A coloured dot for a non-numeric state. **Never colour alone** — the dot always sits beside the formatted value, because colour is exactly the channel a colour-blind user does not have. A boolean is the two-colour case needing no configuration, and `false` is the *neutral* token rather than the down one, since off is not a fault. Multi-state strings map through `config.colorMap` (`{"running": "healthy", "exited": "down"}`); an unmapped value stays neutral rather than being guessed at. The map may only name the four `--status-*` tokens, so a binding cannot put a fifth meaning-carrying hue on a dashboard. |
| `LogStreamWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A scrolling monospace pane over a newline-separated `String` data point — not an array, because a data point declares one value type and a second wire shape for it is how a renderer and a connector quietly disagree. **Auto-scroll follows, it does not force:** it re-pins to the bottom only if it was already there when the update arrived, so a reader who scrolled up is left alone. `role="log"` with `aria-live` deliberately muted — the implied `polite` would have a screen reader announce every line of a pane that updates on every poll. |
| `ActionButtonWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | Runs one action, and the control every action is compatible with: parameterless actions fire straight away, anything else opens the shared `ActionParamsDialog`. Reusing that dialog rather than building a second parameter prompt is the point — two would drift, and the widget one would be the one nobody remembered to fix. |
| `ActionToggleWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A `Switch` that sends a boolean. Optimistic — it moves instantly and **reverts on failure**, which is why `onExecute` must reject rather than swallow: a toggle left on after a failed request lies about the state of a service. **Known limitation, stated on purpose:** it shows what this widget last set, not what the service is. An action binding names an action and nothing else, so there is no data point behind it to read a starting position from; pair it with a `StatusDot` on the boolean data point. Closing that gap is a connector-contract change, not a widget change. |
| `ActionSliderWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A `Slider` that sends a number. **Fires on release, never while dragging** — a drag emits a value per frame, which would be dozens of requests for one gesture, with the added hazard that they arrive out of order and leave the service on a value the user passed through rather than the one they stopped on. Radix separates `onValueChange` from `onValueCommit` for exactly this. Bounds from `config.min`/`max`/`step`. Same "shows what it last sent" limitation as `Toggle`. |
| `ActionTextFieldWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | An `Input` plus a submit button that sends a string. A real `<form>`, so Enter submits the way it does everywhere else and the button needs no separate wiring; `noValidate` so a native validation bubble cannot pre-empt the connector's own `invalidParams` message. Clears on success and **keeps its text on failure**, so a rejected value can be corrected rather than retyped. |
| `ActionSelectorWidget` | `packages/ui-kit/src/widgets` | custom | — | web-frontend, desktop, mobile | A `Select` that sends one of a fixed set of strings. **Options come from `config.options` on the binding, not from the schema's `enum`** — a deliberate simplification matching `SchemaForm`'s existing limitation, because a selector that read `enum` while the generated parameter form ignored it would offer a picker in one place and a free-text box in the other for the same action. When `enum` support lands it belongs in `SchemaForm` first, and this should then prefer the schema with `config.options` as the override. A binding with no options renders a disabled trigger saying so, not an empty menu that looks like loading. |
| `PlacementBindingEditor` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Builds the `widgetBindings` array for a placement, shared by `AddPlacementDialog` (seeded from the connector's `defaultLayout`) and `PlacementBindingsDialog` (seeded from what is stored) — one editor, because the flows differ only in where the starting array came from. A row per binding: a Display/Action `SegmentedControl`, a `Select` for the data point or action, a `Select` for the widget filtered by the compatibility tables, and the config fields that widget needs (gauge/progress bar min–max, slider min–max–step, chart type, a repeatable option list for a dropdown). Changing the target re-picks the widget when the current one no longer fits, rather than leaving a pairing that would render nothing. Rows carry a **minted stable key** rather than their array index: Radix `Select` keeps state by component identity, and a reused instance whose controlled value is no longer among its items clears itself and reports `""` — which is how removing one row could submit an empty widget type for another. Every `onValueChange` also rejects `""` for the same reason. |
| `AddPlacementDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Adds a connector to a dashboard. One dialog rather than a wizard: choosing the instance reveals its widgets below, pre-filled from `defaultLayout`, and both submit together — so someone who wants three of the six widgets deletes three rows instead of placing the card and pruning it afterwards. Auto-selects when only one instance is registered. Size defaults to `metadata.minSize`, the same floor the grid and the backend enforce, so a new card is never born too small to read; position is the crude "below the lowest existing card", since anything cleverer would guess at an arrangement the user is about to change and a card in a surprising gap is harder to find than one at the bottom. `noValidate`, so the backend's own message about a refused binding or size is what the user reads. |
| `PlacementBindingsDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Edits the widgets on an existing placement, sharing `PlacementBindingEditor`. Which connector a placement points at is deliberately not editable: the backend fixes it, and re-pointing a card would silently invalidate every binding on it, so delete-and-add is the honest form of that operation. |
| `ActionParamsDialog` | `packages/ui-kit/src` | custom | — | web-frontend, desktop, mobile | Collects an action's parameters before running it, generated from its own `paramsSchema` through `SchemaForm` so an action gaining a parameter needs no frontend change (same string/number/boolean subset). | `Progress` | `packages/ui-kit/src` | shadcn | — | web-frontend, desktop, mobile | Wraps `@radix-ui/react-progress`.
